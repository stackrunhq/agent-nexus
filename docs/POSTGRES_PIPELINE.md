通过 `NEXUS_TEST_PGVECTOR_URL` 提供专用测试服务器连接，账号必须能创建数据库并安装已具备的 pgvector 扩展。命令为每个场景创建 `nexus_pipeline_` 加随机 UUID 的新数据库，完成或失败后仅删除自己创建的数据库；不把服务器连接指向的原数据库作为业务测试目标。不要在生产服务器执行负载测试。输出目录需存在，指定文件会被覆盖。

## 验证范围

16、64、128 分片场景覆盖上传、实际解析 Worker、发布、pgvector 索引 Worker、检查点取消后恢复、词法/向量/混合检索、引用问答。129 分片验证容量拦截。流程及 HTTP 模拟模型复用 [软件管线基准](PIPELINE_BENCHMARK.md)，不重复维护业务逻辑。

在每个正常场景尾部，把模型日限额调整为当前已用量加一，再并发发送四个向量查询，要求恰好一个 200、三个 429，且只多调用一次 embedding。随后验证索引/模型额度归零后的拒绝。此检查验证准入竞争，不等于四个成功业务任务的吞吐压测。

## 内存与时间

每 20 ms 采样基准 Python 进程 RSS（Linux）或工作集（Windows），记录基线、采样最大值及样本数。不启用 tracemalloc，因此与步骤 37 的 Python 分配值含义不同。

采样包含进程既有内存，短暂峰值可能漏采；不包含解析子进程和 PostgreSQL 内存，也不是整套部署总内存。场景顺序执行，共享解释器缓存，所以后续场景的基线可能升高。模型仍为确定性 HTTP 模拟，TestClient 不经过真实 HTTP 网络；恢复等待被跳过，查询仅少量采样。

三个正常场景均只新增一次模型调用并返回 `[200, 429, 429, 429]`，成功复用首批 16 个分片。以上单次构建时间不能用于推导生产 SLA；所有自建数据库、临时实例和生成凭据已清理。
