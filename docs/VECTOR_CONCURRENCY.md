# pgvector 并发与 Python 内存基准

步骤 37（2026-09-14）。本次验证原生缓存层的并发构建/检索，不是完整 API 管线容量测试。

使用专用、已完成 0012 迁移和 pgvector 初始化的测试数据库，通过环境变量 `NEXUS_TEST_PGVECTOR_URL` 提供连接。不要使用生产数据库。执行：

```sh
python -m agent_nexus_cli.vector_concurrency --output evaluation/results/vector-concurrency-local.json --rounds 10
```

输出目录需存在，指定文件会被覆盖。固定测试 128/1024 行、64 维、1/2/4 个线程；每线程运行 10 次检索（可设 1～100）。每个线程使用独立随机版本 ID 和固定随机种子，完成或异常后删除自己创建的缓存行。数据库初始化与销毁由外部测试环境负责，CLI 不自动升级或删除数据库。

本机使用临时 PostgreSQL 17.11、pgvector 0.8.6；已停止实例并删除生成的凭据。原始结果：[vector-concurrency-2026-09-14.json](../evaluation/results/vector-concurrency-2026-09-14.json)。

| 128 | 1 | 0.264 | 0.99 |

全部线程的 Top-10 与参考精确计算重合率为 100%，最大分数误差低于 1e-5。JSON 保存每线程构建时间、查询中位数、P95 和误差。

整组耗时包含生成数据、构建、Python 参考排序、检索及清理，不等同请求吞吐量。tracemalloc 在测量期间开启，记录本 Python 进程全部线程的受跟踪分配；它不包含 PostgreSQL 内存、大部分 C 扩展分配或系统 RSS。跟踪本身影响延迟，不能与未跟踪基准直接比较。线程也会受到 Python GIL 和参考计算竞争影响。

本次发现较大数据量与并发增加时延迟和 Python 分配明显上升，但样本不足以推导生产容量。1024 行仅用于派生缓存实验，业务 128 分片上限保持。下一步将完整 API/Worker 管线接入隔离 PostgreSQL，分开测量无跟踪延迟、Python/数据库进程 RSS 和并发租户配额。
