# 模型调用的显式索引任务关联

当前步骤 53 已增加 [0017 尝试与批次定位](CALL_BATCH_POSITION.md)，新调用同时记录任务尝试次数和分片区间；下文未区分尝试的描述为步骤 52 历史范围。

步骤 52（2026-09-16），数据库 **0016**，仍为 24 张业务表。

`model_calls` 新增可空的 `index_job_id`，以及 `(tenant_id, index_job_id)` 查询索引。后台索引 Worker 和同步构建接口把持久化任务 ID 传入构建服务、网关与调用账本；调用开始时即保存，因此 pending、成功、失败记录都有归属。记录前校验任务存在、企业和模型一致，并限定 embeddings 能力。此字段不由对外请求参数指定。

任务详情返回的每条调用新增 `index_job_id` 和 `association`：

- `exact`：任务 ID 一致，页面标记“精确任务关联”。其他任务的已关联调用即使请求 ID 相同也不会返回。
- `request_match`：没有任务 ID，按同企业、请求 ID、模型和 embeddings 能力匹配，页面标记“请求匹配（归属未确认）”。可能是历史调用或非任务调用，不能认定精确归属。

响应 `correlation` 更新为 `explicit_task_with_unlinked_request_matches`。两类记录共同分页、逐行区分，不把旧调用自动回填成精确关联。任务重领后继续使用原任务 ID，目前尚不区分每次尝试和分片批次。聊天、检索及未提供持久任务 ID 的内部构建保持空关联。

该字段不设数据库外键，避免账本保留与任务清理互相限制；写入时由服务校验企业/模型归属。任务 ID 不是凭据，详情仍要求管理员并校验完整企业/应用/版本路径。调用成功仍不表示索引最终成功，未知 token 和 pending 的解释不变。

## 升级

先备份并停止 API 与全部 Worker，使用迁移账号执行 `python -m agent_nexus_cli.database upgrade` 至 0016，再统一启动。迁移增加可空列和索引，保留旧记录且不推断关联；无需重建索引数据。SQLite 无版本开发库的历史 0008 校验兼容新增可选列，PostgreSQL 仍走显式迁移。回退使用验证过的备份。
