# 完整软件管线基准

步骤 36（2026-09-14）。当前基准使用独立临时 SQLite、portable 检索后端、FastAPI TestClient 和确定性 HTTP 模型模拟器，不连接业务数据库或外部模型服务。临时目录在结束后清理。

```sh
python -m agent_nexus_cli.pipeline_benchmark --output evaluation/results/pipeline-local.json --rounds 5
```

在已安装项目的 Python 环境执行，输出目录需已存在；指定的输出文件会被覆盖。默认按 16、64、128、129 分片运行，向量 64 维；`--rounds` 允许 1～20 次检索/问答采样。每个场景独立新建并迁移数据库，环境中的模型/索引限额和向量后端仅在基准进程内临时覆盖，结束后恢复。

## 覆盖路径

1. 通过 API 建企业、应用、版本、上传合成 TXT，经解析 Worker 生成分片并发布。
2. 提交索引任务，经 Worker 构建，确认最终索引可用及 embedding 调用数。
3. 再次构建，在首批检查点落库后模拟取消；将该临时任务的租约置为过期，重新领取，验证成功、两次尝试、首批复用和检查点清理。
4. 测量词法检索、向量检索、混合检索及引用问答，验证返回当前文档引用。
5. 将本次临时企业的索引及模型配额设为 0，确认请求被拦截、未额外调用模型。129 分片仅验证容量拒绝和零模型调用。

## 如何解释

这是软件路径基准，不是生产容量承诺：单进程、无真实网络延迟、无并发、仅合成 TXT，模型向量由文本 SHA256 生成，聊天响应固定。引用归属校验不等于真实语义质量评测。构建和恢复各只有一次测量，查询每类仅 5 次，P95 在此采样数下就是最大值。

恢复注入的是取消异常，不是操作系统强杀；租约等待时间被排除。SQLite 与 pgvector 的结果不能直接等同；本次也未覆盖 PDF/DOCX/OCR、真实模型、Docker 或内存峰值。

结论：当前 128 分片流程和恢复调用数量符合预期，继续保留上限。下一步将同类基准扩展到隔离 PostgreSQL/pgvector 和并发任务，测量数据库负载及内存，再评估扩容。
